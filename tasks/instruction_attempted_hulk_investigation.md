# 지시서 — Attempted 라벨 사유 구분 가능성 및 DoS Hulk shortcut 실측 조사

작성일: 2026-09-10
대상: Claude Code
성격: **조사 전용(read-only). 데이터 수정·파이프라인 재실행·정책 확정은 이 작업 범위가 아니다.**

---

## 0. 배경과 목적

`project_context_roadmap.md`의 1·2단계는 2026-09-10에 실행 완료됐으나, 그 과정에서 **두 건의 전제 결정이 정책표(C-2, 1-1~1-12)에 누락된 채 진행됐다**는 사실이 확인됐다.

1. `X-Attempted` 계열 라벨(원본 기준 약 447,362건)의 처리 방침
2. DoS Hulk 클래스의 포함 여부 및 잔존 shortcut 처리

사용자는 두 건에 대해 다음 방향을 결정했다.

- Attempted는 통째로 처리하지 않고 **사유(카테고리)별로 나눠 일부만 채택**한다.
- DoS Hulk는 **제외**하고 shortcut도 배제한다.

그런데 이 방향을 정책 문서로 확정하려면 데이터에서 먼저 확인해야 하는 사실이 있다. 특히 **정제판 CSV에 Attempted의 사유를 구분할 수 있는 정보가 실제로 들어 있는지가 미확인**이며, 없다면 "사유별 차등 채택"이라는 방침 자체가 성립하지 않는다.

이 지시서는 그 확인 작업을 정의한다. 산출물은 **판단 근거가 되는 수치와 사실**이며, 정책 결정은 사용자가 한다.

## 1. 전제와 제약

1-1. 입력 데이터는 `data/CICIDS2017_improved_2022ver/`의 요일별 CSV 5개(1단계 C-8 기준 총 2,099,976행 × 91열)와, 1·2단계 파이프라인이 생성한 최종 학습 테이블 및 `split` 컬럼이다.

1-2. **원본 CSV와 파이프라인 산출물을 모두 조사 대상으로 삼는다.** 파이프라인이 라벨을 가공했을 가능성이 있으므로, 라벨 관련 통계는 반드시 **원본 CSV 기준으로도 독립 산출**해 대조한다.

1-3. 다음은 금지한다.
- 데이터 파일 수정, 행 삭제, 라벨 변경
- 1·2단계 파이프라인 재실행 또는 코드 변경
- 정책 확정, 로드맵 문서 갱신, 정책표 항목 신설
- 조사 결과에 근거한 임의의 후속 처리(예: "제외가 맞아 보이니 미리 필터를 넣어둠")

1-4. 조사 스크립트는 `scripts/investigation/` 아래에 새로 만들고, 기존 파이프라인 모듈은 **import해서 읽기만** 한다.

1-5. 실행 시 커밋 해시와 입력 파일 SHA256을 산출물에 함께 기록한다(정책 1-9와 동일 방식).

1-6. 컬럼명을 추정하지 않는다. `docs/glossary.md`가 아직 없으므로(C-10), 필요한 컬럼은 실제 헤더에서 문자열 매칭으로 해석하고, **매칭에 사용한 실제 컬럼명을 보고서에 그대로 적는다.** 후보가 둘 이상이거나 하나도 없으면 그 사실을 보고하고 해당 작업을 중단한다.

## 2. 작업 1 — 라벨 인벤토리

2-1. 라벨 컬럼의 고유값 전체를 나열하고, 각각의 행 수를 산출한다.

2-2. 다음 축으로 교차 집계표를 만든다.
- 라벨 × 요일
- 라벨 × `split`(train/calib/test)

2-3. 라벨 문자열에서 `Attempted` 계열을 식별하고, 그 명명 규칙을 기술한다(예: `<공격명> - Attempted` 형태인지, 접미사 표기가 일관되는지, 공백·하이픈 변형이 있는지).

2-4. Attempted 계열의 총 행 수를 산출하고, **구 문서가 인용한 447,362건과 대조**한다. 그 수치는 원본(비정제) CIC-IDS2017 기준일 가능성이 있으므로, 차이가 나면 차이 자체를 보고한다. 일치시키려 하지 않는다.

---

## 3. 작업 2 — Attempted 사유 구분 가능성 판정 (최우선)

이 작업의 결과에 따라 사용자의 결정 1이 실행 가능한지가 갈린다.

3-1. CNS2022 논문 Table III(2017 부분)에 등장하는 사유는 다음 7종이다. 이것이 조사 기준이다.
1. Empty Payload
2. No malicious payload
3. Target Unresponsive
4. Port/System Closed
5. Attack startup/tear down artifact
6. Attack artifact
7. Attack Implemented Incorrectly (2018에만 등장 — 2017 범위에서는 부재 확인용)

3-2. 데이터에서 이 사유를 구분할 수 있는 정보가 있는지 다음 순서로 확인한다.
1. 전체 91개 컬럼 헤더를 나열하고, 사유·근거·카테고리·reason·category 등에 해당할 만한 컬럼이 있는지 확인
2. 라벨 컬럼 문자열 자체에 사유가 인코딩되어 있는지 확인(예: `DoS Hulk - Attempted - Empty Payload` 같은 형태)
3. 요일별 CSV에 서로 다른 컬럼 집합이 있는지 확인(한 파일에만 추가 컬럼이 있을 가능성)
4. 저장소 `github.com/GintsEngelen/CNS2022_Code` 로컬 클론에 사유 분류 로직이나 카테고리 번호 매핑이 포함되어 있는지 확인

3-3. 판정을 다음 셋 중 하나로 명시한다.
- **A. 직접 구분 가능** — 사유 컬럼 또는 라벨 문자열에 사유가 존재. 이 경우 사유별 행 수를 라벨 × 사유 교차표로 산출한다.
- **B. 재계산으로 구분 가능** — 사유 컬럼은 없으나 저장소의 라벨링 로직으로 재현 가능. 이 경우 재현에 필요한 입력(PCAP 여부 포함)과 예상 작업량을 기술한다. **재현 자체는 이 작업에서 수행하지 않는다.**
- **C. 구분 불가능** — 위 어느 경로로도 사유를 복원할 수 없음. 이 경우 그렇게 판정한 근거를 구체적으로 적는다.

3-4. 판정이 B 또는 C면, **사용자의 "사유별 차등 채택" 방침이 현재 조건에서 실행 불가능하다는 뜻**이므로 보고서 최상단에 그 사실을 명시한다.

3-5. 저자 웹사이트(`intrusion-detection.distrinet-research.be/CNS2022/`)에 사유 분류 문서나 카테고리 번호 체계가 공개되어 있는지 확인한다. 네트워크 정책상 접근이 막히면 시도했다는 사실과 차단 사유만 기록하고 넘어간다.

## 4. 작업 3 — DoS Hulk shortcut 실측

4-1. 구 문서는 저자 라벨링 문서를 근거로, DoS Hulk가 `Total Length of Bwd Packets`의 **4개 값(11595, 23190, 11606, 23201)** 으로 **545,438 flow 중 8개를 제외한 전부**가 식별된다고 서술한다. 이 주장을 데이터로 직접 검증한다.

4-2. 해당 컬럼의 실제 이름을 헤더에서 확인한다(제약 1-6). CICFlowMeter 계열은 `Total Length of Bwd Packets` / `Bwd Packet Length Total` 등 표기가 갈리므로 추정하지 않는다.

4-3. 다음을 산출한다.
1. 위 4개 값 각각의 전체 데이터 내 출현 행 수
2. 그중 라벨이 `DoS Hulk` 계열(Attempted 포함)인 행 수와 그 외 라벨인 행 수
3. `DoS Hulk` 계열 전체 행 중 위 4개 값에 해당하지 않는 행 수 — 구 문서의 "8개"에 대응하는 수치
4. 위 4개 값을 가진 행 중 **BENIGN인 행 수** — 이 값이 크면 shortcut이 아니라 단순 공통값이라는 뜻이므로 해석이 완전히 달라진다
5. 545,438이라는 모수가 무엇을 세었는지 데이터에서 대응되는 수를 찾을 수 있는지

4-4. 이 4개 값에 의존하지 않는 형태로도 확인한다. `DoS Hulk` 계열 행에서 해당 컬럼의 고유값 분포(상위 20개와 누적 비율)를 산출해, 실제로 소수 값에 집중되는지 본다.

4-5. **다른 클래스에도 같은 종류의 단일 컬럼 shortcut이 있는지 예비 확인한다.** 각 공격 라벨에 대해, 라벨 내 행의 90% 이상을 10개 이하의 고유값으로 덮는 컬럼이 있는지 스캔한다. 이는 정식 feature ablation의 대체물이 아니라 우선순위 판단용 사전 스캔이다.

---

## 5. 작업 4 — 제외 시나리오별 잔존 공격 다양성 집계

두 결정을 적용하면 1·2단계 재실행이 불가피하다. 재실행 전에, 결과적으로 train에 어떤 공격이 얼마나 남는지를 미리 본다. **여기서 남는 클래스가 지나치게 적으면 6단계 LOAO 설계 자체가 성립하지 않는다.**

5-1. 다음 시나리오별로 라벨 × 요일 행 수를 산출한다. 실제 필터링은 메모리 상에서만 수행하고 파일로 쓰지 않는다.

- **S0** 현행(아무 제외 없음) — 대조군
- **S1** `DoS Hulk` 및 `DoS Hulk - Attempted` 전량 제외
- **S2** S1 + Attempted 중 Target Unresponsive·Port/System Closed 계열만 공격으로 채택, 나머지 사유는 제외 — **작업 2 판정이 A일 때만 산출 가능**
- **S3** S1 + Attempted 계열 전량 제외
- **S4** S1 + Attempted 계열 전량을 공격으로 채택

5-2. 각 시나리오에서 다음을 보고한다.
1. 총 행 수, BENIGN 대 공격 비율
2. 공격 라벨별 행 수(0건이 된 라벨 명시)
3. S0 대비 감소분

5-3. 각 시나리오에 대해 2단계 그룹 분할 기준을 적용했을 때 `below_min_group_count`에 걸릴 것으로 예상되는 라벨 목록을 산출한다. 2단계 스크립트의 그룹키 생성·커트라인 판정 함수를 **재실행이 아니라 함수 호출로 재사용**한다. 함수 분리가 되어 있지 않아 재사용이 불가능하면 그 사실을 보고하고 이 항목을 건너뛴다.

5-4. 시나리오별로 **train에 실제로 남는 공격 라벨의 개수**를 명시한다. D-8에서 DDoS가 이미 그룹 수 미달로 전량 test에 배정된 상태이므로, 이 감소가 누적된다는 점을 함께 반영한다.

## 7. 보고 형식

`report.md`는 다음 순서로 쓴다.

1. **판정 요약** — 작업 2의 A/B/C 판정을 첫 문장에 둔다. B나 C면 "사유별 차등 채택은 현재 조건에서 실행 불가능"을 명시한다.
2. **작업별 결과** — 수치 위주. 각 수치가 원본 CSV 기준인지 파이프라인 산출물 기준인지 반드시 표기한다.
3. **구 문서 주장과의 대조** — 447,362건, 545,438 flow 중 8개, 4개 값 shortcut, 약 158k 규모 각각에 대해 실측치와 일치/불일치를 표로 제시한다. **불일치를 일치시키려는 조정은 하지 않는다.**
4. **확인 불가 항목** — 컬럼 매칭 실패, 네트워크 차단, 함수 재사용 불가 등을 사유와 함께 나열한다.
5. **판단이 필요한 지점** — 조사 중 새로 드러난, 사용자 결정이 필요한 사항. 권고는 적되 확정하지 않는다.
