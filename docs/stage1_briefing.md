# 1단계 진행 상황 브리핑 (Claude Code 인계용)

## 0. 이 문서의 목적과 사용법

이 문서는 두 가지 역할을 겸한다.

- **브리핑**: 지금까지 논의를 통해 1단계에서 무엇이 확정되었는지 요약한다.
- **작업 지시서**: Claude Code가 이 문서만으로 1단계 구현을 이어갈 수 있도록, 각 정책의 확정 사항뿐 아니라 **왜 이렇게 정했는지**까지 남긴다. 근거를 모르면 구현 중 "더 단순한 방법"으로 임의 대체할 위험이 있으므로, 이유 설명은 생략하지 말 것.

이 문서는 이전에 전달한 `split_protocol_proposal.md`(2단계 작업 지시서)와 짝을 이룬다. **4장에서 설명하듯 1단계와 2단계는 완전히 분리된 순차 단계가 아니라 일부 상호 의존적**이므로, 두 문서를 함께 참조해야 한다.

## 3. 각 정책의 근거 (임의 변경 금지 — 왜 이렇게 정했는가)

**3-2. 중복 플로우 검출을 두 단계로 나눈 이유**
완전일치는 캡처·전처리 과정의 순수한 버그(패킷 중복, PCAP 파일 겹침)로 명확하다. 완화기준은 같은 플로우가 미세한 값 차이로 다르게 기록된 경우까지 잡기 위함이며, 이때 라벨이 갈리면 이는 **라벨링 로직 자체의 결함**을 가리킬 수 있으므로 자동 삭제 대상이 아니다. → 1-7과 연결.

**3-3. NaN을 대체하지 않고 LightGBM에 위임한 이유**
표준편차 계열 NaN은 "값이 작다"가 아니라 "정의 자체가 불가능하다"는 의미다. 0으로 채우면 이 둘을 혼동시켜 모델이 "표준편차가 0"과 "표준편차가 정의 불가"를 같은 신호로 학습하게 된다. 이는 편도 트래픽·단일패킷 플로우 같은 특정 공격 패턴과 상관되어 있어 잘못 채우면 새로운 누수가 된다. LightGBM의 네이티브 분기 처리는 이 정보를 왜곡 없이 다룰 수 있는 유일한 방법이다.

**3-4. Infinity를 별도로(0 대체 아님) 클리핑하는 이유**
LightGBM 네이티브 결측 처리는 NaN에만 적용되고 Infinity는 결측으로 인식되지 않아 그대로 두면 이후 파이프라인(확률 보정의 로그손실, SHAP 배경 데이터셋 통계, OOD 거리 계산)에서 수치 오류를 일으킨다. **반드시 train split에서만** 클리핑 기준값을 계산해야 하는 이유는 calib/test 정보가 클리핑 기준에 섞이면 그 자체로 데이터 누수이기 때문이다.

**3-5. Destination Port를 삭제하되 보존하는 이유**
IP·Flow ID·Timestamp와 달리 포트는 실시간 조기 피처로 정당화될 여지가 있다(3단계 "실시간성 정의"와 직결). 지금 완전 삭제하면 3단계 결정에 따라 데이터를 재생성해야 하므로, 되돌릴 수 있는 형태로 분리 보존한다.

**3-6. 상수/중복 컬럼 판단을 train 기준으로 하는 이유**
전체 데이터가 아니라 train split에서만 판단해야, calib/test에만 존재하는 값 분포 정보가 컬럼 선택에 섞이는 것을 막는다(2단계 그룹 기반 분할 원칙과 동일한 논리).

**3-9. 다운로드 날짜 대신 커밋 해시를 재현성 기준으로 삼는 이유**
정확한 다운로드 시점은 사후에 복원할 수 없는 정보다. git 커밋 해시는 검증 가능하고 명확한 대체 기준이며, 로컬 clone이 없다면 현재 시점에 재clone하여 얻은 커밋 해시와 보유 CSV의 SHA256을 대조해 버전 일치 여부를 확인하는 방식으로 우회한다.

## 4. 중요 구조적 참고사항 — 1단계와 2단계는 완전 순차가 아니다

1-4(클리핑), 1-6(상수/중복 컬럼), 1-8(클리핑 배수)은 모두 **"train split 기준"**으로 계산해야 한다. 그런데 train/calib/test 구분은 2단계 분할 프로토콜(`split_protocol_proposal.md`)의 산출물이다. 따라서:

- 1단계를 "먼저 100% 끝내고" 2단계로 넘어가는 것이 불가능하다.
- 올바른 실행 순서는 5장과 같이 **1단계 전반부 → 2단계 → 1단계 후반부**로 인터리빙된다.
- Claude Code가 이 문서와 `split_protocol_proposal.md`를 각각 독립 작업으로 순서 없이 실행하면 3-4, 3-6의 누수 방지 원칙이 깨지므로, 반드시 5장의 통합 순서를 따를 것.

---

## 5. 통합 실행 순서 (1단계 + 2단계)

1. **[1단계]** 데이터 로드, `dataset_manifest.json` 생성 (1-9)
2. **[1단계]** 중복 플로우 검출 및 처리 (1-2, 1-7)
3. **[1단계]** Destination Port 분리·보존 (1-5)
4. **[2단계]** 그룹키 생성 → 요일×레이블 커트라인 → split 라벨 부여 → LOAO 마스크 후처리 (`split_protocol_proposal.md` 4장 참조)
5. **[1단계]** train split 기준 상수/중복 컬럼 판단 및 제거 (1-6)
6. **[1단계]** train split 기준 클리핑 값 계산(1-8) 및 전체 split에 적용(1-4)
7. **[1단계]** 최종 학습 테이블 완성 및 저장

3단계(피처 설계)는 7번 산출물을 입력으로 시작한다.

## 6. 산출물

- `dataset_manifest.json` — 소스 검증 정보
- `duplicate_flow_report.{json,csv}` — 완전일치/완화기준 중복 검출 건수, 라벨 충돌 건수
- `reserved_for_early_features.parquet` — Destination Port 등 보류 컬럼 원본값
- `dropped_constant_duplicate_columns.json` — 1-6에서 제거/유지된 컬럼 목록과 판단 근거(train 기준 통계)
- `clipping_values.json` — 1-8에서 계산된 컬럼별 클리핑 상한값 (train 기준)
- 최종 학습 테이블 (parquet) — 2단계 `split` 컬럼 포함, 중복 제거·컬럼 정리·클리핑 완료 상태

## 7. 검증 기준

- [ ] 완전일치 중복이 최종 테이블에 0건인지 assert
- [ ] `label_conflict_flag=True` 행은 삭제되지 않고 남아 있는지 확인
- [ ] 상수/중복 컬럼 판단이 calib/test 값을 전혀 참조하지 않았는지 코드 경로 확인
- [ ] 클리핑 상한값이 calib/test 값을 전혀 참조하지 않았는지 확인
- [ ] Destination Port가 기본 테이블에는 없고 `reserved_for_early_features`에는 있는지 확인
- [ ] `dataset_manifest.json`에 `original_download_date` 필드가 존재하지 않는지(임의로 채워 넣지 않았는지) 확인

## 8. 명시적 비목표

- CSE-CIC-IDS-2018 처리 — 범위 아님 (1-10)
- 결측치 수치 대체(0, 평균 등) — 3-3 근거에 따라 금지
- 상수/중복 컬럼 판단이나 클리핑 값 계산 시 전체 데이터(calib/test 포함) 사용 — 누수이므로 금지
- Destination Port의 최종 사용 여부 확정 — 3단계로 이연, 지금 결정하지 않음
